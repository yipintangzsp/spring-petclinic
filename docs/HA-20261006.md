# PetClinic 跨节点部署与维护演练 · 2026-10-06

## 根因与边界

基线三个 Pod 为 `petclinic-85b4dc85bd-{88dls,pcf7f,wlxxs}`，全部位于 devops。真实原因是 Deployment 的硬选择器 `kubernetes.io/hostname: devops`，并非 scheduler 随机选择、镜像仅支持 arm64、worker NotReady 或资源压力。已有 `ScheduleAnyway` 拓扑分散规则和 cloud toleration 无法突破该选择器。

三个节点均 Ready、kubelet 正常上报，无 MemoryPressure/DiskPressure/PIDPressure，无 cordon。devops arm64、6 CPU/约 19.5GiB；aliyun amd64、2 CPU/约 1.57GiB；ucloud amd64、2 CPU/约 3.78GiB。worker 保留 `cloud=true:NoSchedule` 和 limited-cloud/expiry-risk/important-workloads=avoid 标签；PetClinic 已有相应 toleration，标签本身不是 scheduler 的禁止规则。现场 requests：devops 2680m/11246Mi；aliyun 10m/50Mi；ucloud 260m/1074Mi。ucloud 还承载 Trino；本轮不更改它。云节点的到期风险依然存在。

应用没有 PVC，只有可选 ConfigMap volume；default ServiceAccount、禁挂 API token、non-root/securityContext、探针、100m/256Mi requests、500m/768Mi limits、45s graceful termination、PDB minAvailable=2 和镜像 0.9.0-ci-101 全部保留。共享 PostgreSQL、local-path PVC、Ingress、控制平面和主要监控仍依赖 devops。本轮提供应用层跨节点副本与自愿维护验证，**不证明 devops 物理故障后整个业务仍可用**，不把单实例数据库称为 HA。

## 维护演练与回滚方法

选择 aliyun-worker，避免 devops 上的共享数据库/控制平面/平台组件，以及 ucloud 的 Trino。`run-ha-maintenance.py` 在执行前核对节点未 cordon、三节点各一副本、目标节点其他 Pod 全是 DaemonSet、PetClinic 无 PVC/emptyDir，并执行 server dry-run。实际命令：

```sh
kubectl drain aliyun-worker --ignore-daemonsets --pod-selector=app=petclinic --dry-run=server --timeout=60s
kubectl cordon aliyun-worker
kubectl drain aliyun-worker --ignore-daemonsets --pod-selector=app=petclinic --timeout=120s
kubectl uncordon aliyun-worker
```

**这是只驱逐 PetClinic 的维护演练，不是完整节点清空或物理故障模拟。** 不使用 force、disable-eviction、delete-emptydir-data，不重启机器。finally 无论成功失败均停止未结束的 drain 并 uncordon。依据：[kubectl drain](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_drain/)。

检查顺序：初始 Eviction dryRun=All HTTP 201→实际 drain 使用 Eviction→预算归零后对第二个健康 Pod 发 dry-run Eviction 并要求 HTTP 429→ReplicaSet 补齐 Pod 于剩余节点→EndpointSlice 删除旧 Ready 路由并加入新 Ready 路由→Ingress 与 ClusterIP 两条 `/owners` 请求链路每约 0.5 秒持续检查→真实 Prometheus 时序和 Loki 前后日志→目标节点其他 Pod UID 未变→uncordon。

PDB 只保护自愿驱逐，不保证硬件掉电、OOM、网络分区或 Deployment rollout 的可用副本数。rollout 仍由 maxUnavailable=0 保护。uncordon 不会自动搬迁已运行副本；恢复三节点分布需后续受控发布/驱逐，不能把 uncordon 宣称成自动再平衡。

Git 是回滚权威：撤销本轮 placement 提交，经 Argo 观察旧 selector 和 devops 三副本恢复，再撤销该回滚以重启跨节点版本。禁止 rollout undo 与 selfHeal 相互竞争。不改副本数、不恢复数据库/PVC、不覆写 Secret。

## HPA 前置条件与下一阶段

本阶段不创建 HPA。`metrics-api.json` 记录三次真实 Metrics API 采样：APIService Available=True，三个 NodeMetrics 均存在，PetClinic 有 CPU/Memory usage；阶段内 `kubectl top nodes`/`top pods -n petclinic` 也正常。短期现场验收通过不代表全天网络与 Metrics API 稳定性已证明。

进入 CPU HPA 2–6 之前，先核对：

1. memory request=256Mi 小于已观察到约 430Mi 常驻工作集，按负载/启动峰值调整应用 request，再验收共享容量；不拿 scheduler 的 request 空余量当实际内存空余量。
2. aliyun 总内存仅约 1.57GiB，当前只验证稳定承载一个实例，不允许直接假设扩容到六个时该节点承载两个 JVM 仍安全；评估节点/系统保留内存与 N-1 容量，必要时约束应用容量范围或提高该节点规格。不要为了扩容修改全局 taint/其他业务。
3. HPA 最小副本数 2 与 PDB minAvailable=2 会使两副本时的自愿驱逐预算为 0。维护前临时把 HPA 最小副本数提升至 3并等 Ready/PDB 预算恢复，或单独评估可接受的 PDB 语义，不在演练时绕过 PDB。
4. 再次验证 Metrics API，限定压力测试到 PetClinic，记录 CPU→扩容→多节点分布→请求/延迟→降载→缩容；日志、HTTP 和实例数需同时验收。未完成容量与 PDB 联动前，不声明低风险 HPA 已就绪。
