## 资源、持久化与运维

requests 100m/256Mi，limits 500m/768Mi，Erlang 2 schedulers/4 async threads；内存报警384MiB，磁盘报警1GB；2Gi local-path PVC（容量申请不是宿主文件系统硬配额）。每条消息最大1MiB，vhost `petclinic` 的 classic 队列通过持久化 operator policy 限制每队列10000条/64MiB，满时 reject-publish。该策略不限制队列总数量，实验时仍须及时消费并清理自己创建的队列。

AMQP 仅允许 data-infra、petclinic、ns-apps、ns-devops 命名空间；管理端仅允许现有 Traefik 命名空间；metrics 仅允许 monitoring。没有额外开放 NodePort 或宿主 AMQP 监听。保留系统/业务储备和共享重任务 Lease；新增100m/256Mi请求必须计入后续分析准入，不能沿用安装前预算。

```sh
ssh zhang@192.168.1.58 'sudo kubectl -n data-infra get sts,pod,pvc,svc,ingress | grep rabbitmq'
ssh zhang@192.168.1.58 'sudo kubectl -n data-infra logs rabbitmq-0 --tail=200'
ssh zhang@192.168.1.58 'sudo kubectl -n data-infra exec rabbitmq-0 -- rabbitmq-diagnostics -q check_local_alarms'
ssh zhang@192.168.1.58 'sudo kubectl -n data-infra exec rabbitmq-0 -- rabbitmqctl list_queues -p petclinic name messages_ready messages_unacknowledged consumers'
```

排错先看 Events、日志、alarm、消费 ACK/积压与连接状态；不要删除 PVC 或重置数据库来修复认证。重试测试必须使用新的批次/队列名，或明确恢复本轮队列的消息状态，不能批量删除其他队列。需要按需关闭时，提交 StatefulSet replicas=0 并走现有流程，再将 Argo 固定到通过检查的源码；PVC保留。恢复为1，保持同一节点名/持久卷。手动 scale 会被 selfHeal 恢复。

PVC 模板中的 apiVersion/kind/volumeMode 显式记录 API 默认值；Argo 只忽略嵌套模板自动生成的 status，不忽略 PVC 真实状态、镜像、资源上限、Pod 就绪或整个 StatefulSet spec。源码版本按已通过 CI 的提交固定，不能让 main 上尚未通过的功能变更提前同步。

队列策略来自 `queue-policy.json`，在 broker 初始化后通过 rabbitmqctl 设置并保存在 broker 数据库中；不是另一个常驻控制器。命令示例（在服务器上使用现有 sudo kubectl 权限执行）：

```sh
kubectl -n data-infra exec rabbitmq-0 -- rabbitmqctl set_operator_policy -p petclinic --apply-to classic_queues platform-learning-bounds ".*" '{"max-length":10000,"max-length-bytes":67108864,"overflow":"reject-publish"}'
```

安装期间修复的仓库兼容性故障见 `infra/harbor/registry-arm64-build.md`。全局 QEMU 已恢复原版本，原生 registry 和 registryctl 保留；后续 AMD64 全量清缓存构建的 libc/QEMU 兼容性仍是独立限制，不能用本轮缓存命中的多架构发布宣称它已解决。

参考原理：[官方确认机制](https://www.rabbitmq.com/docs/confirms)、[资源 operator policy](https://www.rabbitmq.com/docs/4.2/policies)、[原生监控](https://www.rabbitmq.com/docs/4.2/prometheus)。
